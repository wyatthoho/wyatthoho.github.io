## Introduction

In this article, pyproject.toml is introduced to demonstrate the basic usage of pyproject.toml. Before that, we have to build concepts of packaging, install, and executable.

---

## Why We Need Packaging

The simplest way to structure a project is two files sitting side by side:

```
project_1/
├── foo.py
└── main.py
```

`foo.py` just prints something:

```python
# project_1/foo.py
print("foo")
```

`main.py` imports it by module name and calls it:

```python
# project_1/main.py
import foo
```

This works fine as long as you run it from inside `project_1/`, since `''` (the current directory) is in `sys.path`:

```
$ cd project_1
$ python main.py
foo
```

**The problem** shows up once you try to reuse `project_1` elsewhere. Say you copy the whole folder into a new project, `project_2`, and want to call into it as a subpackage:

```
project_2/
├── main.py
└── project_1/
    ├── foo.py
    └── main.py
```

`project_2/main.py` tries to import `project_1` as a subpackage:

```python
# project_2/main.py
import project_1.main
```

Now the import breaks:

```
$ cd project_2
$ python main.py  
Traceback (most recent call last):
  File "C:\temp\main.py", line 1, in <module>
    import project_1.main
  File "C:\temp\project_1\main.py", line 1, in <module>
    import foo
ModuleNotFoundError: No module named 'foo'
```

`foo.py` was only importable because `project_1/` itself used to be the current working directory. Once `project_1` becomes a subfolder of `project_2`, that assumption no longer holds.

One fix is to rewrite the import inside `project_1` to be absolute, instead of relying on the working directory:

```python
# project_2/project_1/main.py
import project_1.foo
```

That works for this toy example, but it doesn't scale: if `project_1` were a large codebase, rewriting every import statement by hand — and keeping them correct wherever the code gets reused — isn't realistic. What's needed instead is a way to make a project reusable without touching its internals. That's what **packaging** solves.

# Python Packaging Notes

## Prerequisite: How Python Import Works

When Python starts, it scans a fixed set of paths (`sys.path`). Only modules found under these paths can be `import`ed:

```python
import sys
print(sys.path)
# ['', '/usr/lib/python3.11', '.../site-packages', ...]
```

- `''` (empty string) — the **current working directory**
- `/usr/lib/python3.11` — the standard library
- `site-packages` — where third-party packages live

### Inside a venv

When using a venv, `sys.path` prioritizes the venv's own site-packages over the system's. This is the core isolation mechanism of venv.

The path differs by OS:

```
Windows:   venv\Lib\site-packages
Linux/Mac: venv/lib/python3.11/site-packages
```

---

## Goal: Make Imports Work Regardless of Working Directory

Without any setup, if you place `my_project/` directly in the project root:

```bash
cd my_project
python -c "import my_project"  # ✅ works ('' is in sys.path)

cd /tmp
python -c "import my_project"  # ❌ ModuleNotFoundError
```

**Solution: install the package into site-packages** so it's importable from anywhere in the same environment.

---

## The Pitfall: Why You Need the `src/` Layout

If the package sits directly in the project root:

```
my_project/
├── my_project/   ← package here
└── tests/
```

When running tests from the root, Python finds `my_project/` via `''` in `sys.path` and **bypasses site-packages entirely**. You think you're testing the installed version, but you're not.

**The `src/` layout fixes this:**

```
my_project/
├── src/
│   └── my_project/   ← package is here
└── tests/
```

Now `''` can't resolve `my_project/` directly, forcing you to go through the install step. Tests always run against the installed version.

---

## The Config: `pyproject.toml`

`pyproject.toml` is the modern Python project config file. `pip install` recognizes it by default.

When using setuptools, you need to explicitly point it to the `src/` directory:

```toml
[build-system]
requires = ["setuptools>=64"]
build-backend = "setuptools.build_meta"

[project]
name = "my_project"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = []

[tool.setuptools.packages.find]
where = ["src"]   # ← critical: tells setuptools to look inside src/
```

Without `where = ["src"]`, setuptools looks in the project root by default and won't find `src/my_project/`.

---

## Two Ways to Install

### `pip install .` (regular install)

1. pip reads `pyproject.toml`
2. setuptools finds `src/my_project/` via `where = ["src"]`
3. **Copies the code into site-packages**
4. The running code lives in site-packages

> Downside: after editing source files, you must re-run `pip install .` to see the changes.

### `pip install -e .` (editable install, for development)

1. pip reads `pyproject.toml`
2. setuptools finds `src/my_project/` via `where = ["src"]`
3. **Creates a pointer in site-packages** (a `.pth` file or link) pointing to your local `src/` directory
4. The running code lives in your local `src/`

> Upside: edits to source files take effect immediately on the next import — no reinstall needed.

Files created in site-packages:

```
site-packages/
├── my_project.egg-link              # older setuptools
└── __editable__.my_project...pth    # newer setuptools
```

---

## Defining Entry Points: `[project.scripts]`

After packaging, you can expose CLI commands via `[project.scripts]`:

```toml
[project.scripts]
spam-cli = "spam:main_cli"
```

After `pip install .`, an executable `spam-cli` is created in the venv's `Scripts/` (Windows) or `bin/` (Linux/Mac). It's essentially a wrapper for:

```python
import sys
from spam import main_cli
sys.exit(main_cli())
```

With `pip install -e .`, the executable is still created in `Scripts/bin/`, but it points to the live source in `src/` — so editable mode works for CLI tools too.

---

## Verifying the Install

```bash
pip install -e .
python -c "import my_project; print(my_project.__file__)"
# Should print: .../src/my_project/__init__.py
```

If the path doesn't contain `src/`, setuptools didn't pick up the package correctly.
